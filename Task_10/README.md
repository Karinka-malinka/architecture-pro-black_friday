## Переход на Cassandra

**1. Order History (История завершенных заказов)**
- **Почему**: 
  - Read-only: завершенные заказы не меняются (статус final)
  - Append-only: исторические данные для аналитики
  - Огромный объем: 100M+ завершенных заказов
  - Нужна высокая доступность для просмотра истории
  
- **Преимущества Cassandra**:
  - ✅ Time-series оптимизация (order_date)
  - ✅ Компакция для экономии места
  - ✅ Быстрое чтение истории пользователя
  - ✅ Равномерное распределение по user_id
  
- **Что остается в MongoDB**:
  - ⚠️ **Активные заказы** (pending, processing) - нужны транзакции с products.stock

**3. User Sessions (Пользовательские сессии)**
- **Почему**:
  - Very write-heavy: каждое действие пользователя
  - TTL: автоматическое удаление старых сессий
  - Высокая частота одновременных сессий
  
- **Преимущества Cassandra**:
  - ✅ Очень быстрая запись
  - ✅ TTL автоматически
  - ✅ In-memory таблицы (опционально)

**4. Events (События, аналитика)**
- **Почему**:
  - Write-only: только вставка, без изменений
  - Time-series: события по времени
  - Огромный объем: миллионы событий/день
  
- **Преимущества Cassandra**:
  - ✅ Time-series workload
  - ✅ Компакция (экономия места)
  - ✅ Не нужна ACID


## Концептуальная модель для критически важных сущностей

Ниже представлена концептуальная модель данных, разработанная с учетом требований к производительности, масштабированию и целостности данных для критически важных сущностей интернет-магазина. 


### 1. Order History

**Описание:** История завершенных заказов является read-only и append-only. Данные распределяются равномерно по user_id, обеспечивая быстрое получение полной истории конкретного пользователя.

**Partition Key:** user_id
**Clustering Key:** order_date DESC (для временной последовательности запросов)

**Модель данных:**
```sql
CREATE TABLE order_history (
    user_id UUID,
    order_id UUID,
    order_date TIMESTAMP,
    total_amount DECIMAL,
    items FROZEN<LIST>,
    PRIMARY KEY ((user_id), order_date)
) WITH CLUSTERING ORDER BY (order_date DESC);
```

**Преимущества выбора ключей:**

- **Partition Key (`user_id`):** Обеспечивает равномерное распределение данных по узлам, так как количество пользователей значительно превышает число узлов.
- **Clustering Key (`order_date DESC`):** Гарантирует эффективную сортировку по времени завершения заказа, позволяя быстро получать последние заказы пользователя.

### 2. User Sessions

**Описание:** Пользовательские сессии характеризуются огромным объемом записей и частым добавлением новых данных. Используется временная отметка (session_start_time), чтобы эффективно удалять старые сессии с помощью TTL.

**Partition Key:** user_id
**Clustering Key:** session_start_time DESC

**Модель данных:**
```sql
CREATE TABLE user_sessions (
    user_id UUID,
    session_id UUID,
    session_start_time TIMESTAMP,
    device_type TEXT,
    location TEXT,
    PRIMARY KEY ((user_id), session_start_time)
) WITH CLUSTERING ORDER BY (session_start_time DESC) AND default_time_to_live = 30 * 24 * 3600; // 30 days TTL
```
**Преимущества выбора ключей:**

- **Partition Key (`user_id`):** Минимизирует вероятность горячих партиций, поскольку каждый пользователь генерирует относительно небольшой объем сессий.
- **Clustering Key (`session_start_time DESC`):** Поддерживает хронологический порядок сессий, упрощая поиск последней активности пользователя.

⎯⎯⎯⎯⎯⎯⎯⎯⎯⎯
### 3. Events (аналитика)

**Описание:** Таблица событий используется исключительно для записи действий пользователей, формируя огромный поток данных, преимущественно time-series. Записи хранятся навсегда и используются для анализа поведения пользователей.

**Partition Key:** event_type
**Clustering Key:** timestamp ASC

**Модель данных:**
```sql
CREATE TABLE events (
    event_type TEXT,
    timestamp TIMESTAMP,
    user_id UUID,
    event_data MAP<TYPE>,
    PRIMARY KEY ((event_type), timestamp)
) WITH CLUSTERING ORDER BY (timestamp ASC);
```
**Преимущества выбора ключей:**

- **Partition Key (`event_type`):** Распределяет нагрузку равномерно среди разных типов событий, предотвращая перегрузку отдельных узлов.
- **Clustering Key (`timestamp ASC`):** Упрощает анализ временных серий, облегчая фильтрацию событий по периодам.

### Выбор модели с точки зрения «горячих» партиций и минимизации влияния шардинга

При выборе структуры таблиц были учтены следующие факторы:

- Предотвращение горячей партиции: Использование уникальных значений (например, UUID) в качестве первичного ключа способствует равномерному распределению данных и предотвращает создание крупных секций данных ("hot partitions").
- Минимизация влияния шардинга: Composite keys (композитные ключи) помогают снизить влияние изменений топологии кластера путем оптимизации доступа к данным. Композитные ключи позволяют производить быструю фильтрацию и упорядочивание записей.
- Оптимизация запросов: Введение clustered columns (кластерных столбцов) значительно ускоряет процесс выполнения запросов и уменьшает нагрузку на сервер.

Таким образом, предложенная структура данных обеспечит эффективное управление критическими ресурсами интернет-магазина в условиях экстремальной нагрузки, сохраняя целостность данных и предотвращая деградацию производительности.

## Стратегии обеспечения целостности данных в Cassandra

Для различных сущностей интернет-магазина рекомендуется применять соответствующие стратегии, учитывая компромисс между временем реакции (latency) и гарантией согласованности.

### Order History
Используем **Hinted Handoff** для быстрой записи исторических данных и **Anti-Entropy Repair** для периодического выравнивания данных. Согласованность уровня READ REPAIR можно оставить минимальной, так как это исторический архив, и точные временные отклонения могут быть терпимы.

### User Sessions
Из-за огромного объема и требования высокой скорости обработки лучше использовать **Hinted Handoff** для быстрого сохранения сессий, а антиэнтропийный ремонт запустить по расписанию, учитывая низкую частоту обращений к старым сессиям.

### Events
Использоваем **Read Repair** для гарантированного получения свежих данных при анализе, чтобы снизить риски неправильных выводов из устаревших данных. Дополнительно рекомендуется включить **Anti-Entropy Repair** для предотвращения накопления небольших расхождений.
